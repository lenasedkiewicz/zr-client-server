## How to work through this plan

- **One batch = one branch = 2–3 tasks = 2–3 commits.** Branch from an up-to-date `master`,
  do the tasks in order, open a PR, merge it, then start the next batch from the new
  `master`. Small PRs are easier to review and you can roll one back without the others.
  ```
  git checkout master
  git pull --ff-only
  git checkout -b fix/server-survives-bad-client
  ```
- **Each task goes through `learn-by-commit`:** briefing → approval → code + test → journal
  entry (next free number, from `009`) → commit. Each task below gives the briefing's raw
  material: the finding, the files, the acceptance checks and the "Read first" links.
- **Hints, not solutions.** The reviewer asked guiding questions instead of giving fixes on
  purpose. Each task lists **Answer before coding** questions. Answer them in your own
  words in the briefing before you look at an implementation. They are good quiz material
  for the journal entry too.
- **Regression check after every server fix:** the test ends by connecting a *new* client
  and checking it still gets an answer (for example `help`, or `info` after login). This
  is the reviewer's control question: "does the server still answer a new client?"
- **Versioning:** each batch with a `fix:` commit is a release candidate. Bump `PATCH`
  (`0.1.0-alpha` → `0.1.1-alpha`, ...) in `config.py` when you merge a batch you want to
  call a release (see concept 001). Bumping is your call, so no task forces it.
- **Order matters for batches 1–2:** critical fixes first (the review says "before merge"),
  then the test foundations every later batch builds on. You can reorder batches 3–9 if
  something becomes more urgent. Batches 4 and 5 both change `protocol.py`, so do them in
  order.

## Batch 1: the server survives a bad client (critical)

Branch `fix/server-survives-bad-client`. This is the reviewer's "do now, before merge"
list.

### Task 1.1: a failed send ends only that connection

- **Finding (critical):** `handle_client` (`server.py:142`) protects only the read.
  The two `send_message` calls aren't protected. One of them is inside the
  `except json.JSONDecodeError` block, and the `except (ConnectionError, OSError)` next to
  it can't catch errors raised inside a sibling handler. A `BrokenPipeError` or
  `ConnectionResetError` escapes `serve_forever`, and its `finally` closes the listening
  socket. The reviewer stopped the server with one client that sent a few commands and
  hung up.
- **TLS note:** over TLS a failed write can also raise `ssl.SSLError`. It's a subclass of
  `OSError`, so check the hierarchy before you add another class to an `except`.
- **Do:** make sure that no error on one connection can leave `handle_client`. Every
  network call in the loop, including the send in the error branch, must have the same
  protection as the read.
- **Test (fails before the fix):** a client sends several requests and closes or resets
  the socket without reading the replies. Then a new client connects and gets an answer.
  To force a reset rather than a clean close, look up `SO_LINGER` with a zero timeout in
  the `socket` docs and note in the journal why that sends RST instead of FIN.
- **Answer before coding:**
  1. Which calls in the loop touch the network? Which of them are inside a `try` whose
     `except` actually covers them?
  2. Why can't an `except` clause catch an exception raised in a *sibling* `except`
     block?
  3. Should one client's error ever reach `serve_forever`? What should it do instead?
- **Commit:** `fix: keep serving when sending a reply to a client fails`
- **Read first:**
  - [Errors and exceptions, try/finally](https://docs.python.org/3/tutorial/errors.html#defining-clean-up-actions): Python tutorial
  - [BrokenPipeError](https://docs.python.org/3/library/exceptions.html#BrokenPipeError) and the [exception hierarchy](https://docs.python.org/3/library/exceptions.html#exception-hierarchy)
  - [Python try and except statements](https://www.freecodecamp.org/news/python-try-and-except-statements-how-to-handle-exceptions-in-python/): freeCodeCamp, beginner-friendly
  - [Socket Programming HOWTO](https://docs.python.org/3/howto/sockets.html): what a dead connection looks like at the socket level

### Task 1.2: any malformed input gets an error reply, never a crash

- **Finding (critical):** only `json.JSONDecodeError` is caught. The reviewer crashed the
  server with three inputs:
  - bytes that aren't valid UTF-8 → `UnicodeDecodeError`, raised by `readline()` on the
    text-mode `makefile`
  - syntactically valid JSON with an integer of more than 4300 digits → a plain
    `ValueError`, not a `JSONDecodeError`
  - deeply nested JSON → `RecursionError`. The depth needed depends on the Python
    version: 2000 levels was reported to be enough on 3.10–3.11.
- **Do:** sort the failures on the bytes → text → JSON path into "reject this message,
  keep the session" and "end this session". Write the decision in the code comment and in
  the journal. If you look at the `errors=` argument of `makefile`, choose it on purpose:
  `"ignore"` and `"replace"` silently change the message instead of rejecting it.
- **Test (one per input):** send each input, check the reply, or that only this
  connection closes if that is your decision. Then check that a new client still gets an
  answer.
- **Answer before coding:**
  1. What does `UnicodeDecodeError` inherit from, and what does `JSONDecodeError` inherit
     from? Would `except ValueError` catch both? Would it catch `RecursionError`?
  2. After a decoding error in a *text* stream, is the stream still usable for the next
     line? (Decide, then check by experiment.)
  3. Why does Python limit int-to-str conversion at all? (Hint: the docs say why.)
- **Commit:** `fix: reply with an error to malformed input instead of crashing`
- **Read first:**
  - [UnicodeDecodeError](https://docs.python.org/3/library/exceptions.html#UnicodeDecodeError) and [RecursionError](https://docs.python.org/3/library/exceptions.html#RecursionError)
  - [Integer string conversion length limitation](https://docs.python.org/3/library/stdtypes.html#integer-string-conversion-length-limitation): note the reason, "to mitigate denial of service attacks"
  - [OWASP: Denial of Service](https://community.owasp.org/attacks/Denial_of_Service)
  - [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html): allowlist validation at a trust boundary

**Concept note candidates for this batch** (ask the question and the skill saves the note):
"What is a trust boundary?" and "How does Python's exception hierarchy decide what an
`except` catches?"

## Batch 2: test foundations

Branch `test/test-foundations`. Every later batch adds tests, so make them reliable and
cheap first.

### Task 2.1: no race at start-up, cleanup that always runs

- **Finding (recommended):** `setUp` (`tests/test_server.py:37`) connects as soon as the
  thread starts, but `listen()` runs *inside* that thread. That's a race: on Linux it can
  make a test fail now and then. `tearDown` sends `stop` first, so if that raises, the
  socket and file stay open and the thread is never joined.
- **Do:** have the server signal "listening" (for example with `threading.Event`) and make
  the test wait for that signal with a timeout. Register each cleanup with `addCleanup`
  right after the resource is created.
- **Test:** the suite passes. Optionally add a test that the readiness signal is set only
  after `listen()`.
- **Answer before coding:** Why does `connect()` sometimes succeed before `listen()` and
  sometimes not, depending on the OS? What does `addCleanup` give you that `tearDown`
  doesn't?
- **Commit:** `test: wait for the server to listen and register cleanups`
- **Read first:**
  - [threading: Event objects](https://docs.python.org/3/library/threading.html#event-objects)
  - [TestCase.addCleanup](https://docs.python.org/3/library/unittest.html#unittest.TestCase.addCleanup): runs even when `setUp` fails
  - [Race condition](https://en.wikipedia.org/wiki/Race_condition): Wikipedia

### Task 2.2: unit tests for `handle_request` and `protocol.py`, without sockets

- **Finding (important):** every test goes through a real socket and thread. Even the
  version test starts a server. Nothing tests `protocol.py`, `client.py` or `run.py`
  directly.
- **Do:** create `tests/test_protocol.py`, using `io.StringIO`/`io.BytesIO` as the "socket
  file", and a test class for `Server.handle_request` that calls it directly with a
  session dict. Move the version test into a class that starts no server. Keep the
  end-to-end tests for the main scenario, TLS and `stop`.
- **Test:** cover every request shape: not an object, missing `command`, a non-string
  command, bad `args`, unknown, login required, ok. Also check that `stop` sets
  `running = False`, which is its one side effect.
- **Answer before coding:** Which bugs can only an end-to-end test find, and which are
  cheaper to find in a unit test? Where does this repo sit on the test pyramid today?
- **Commit:** `test: unit-test request handling and the protocol without sockets`
- **Read first:**
  - [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html): martinfowler.com
  - [Unit testing Python functions with unittest](https://www.freecodecamp.org/news/how-to-write-unit-tests-for-python-functions/): freeCodeCamp

### Task 2.3: the SemVer test checks the whole string, in ASCII

- **Finding (recommended):** the `SEMVER` regex (`tests/test_server.py:29`) accepts
  non-ASCII digits (`\d` matches every Unicode digit) and a trailing `\n` (`$` also matches
  just before a final newline).
- **Do:** fix both problems and add negative cases: Arabic-Indic digits, a trailing
  newline, a leading `v`.
- **Answer before coding:** What do `\d` and `$` match in a `str` pattern by default?
  What changes with `re.ASCII` and `re.fullmatch`?
- **Commit:** `test: make the SemVer check strict (ASCII digits, whole string)`
- **Read first:** [re.ASCII](https://docs.python.org/3/library/re.html#re.ASCII),
  [re.fullmatch](https://docs.python.org/3/library/re.html#re.fullmatch),
  [semver.org (PL)](https://semver.org/lang/pl/)

## Batch 3: logging and small clean-ups

Branch `refactor/logging-and-cleanups`. This comes early on purpose: later batches add new
log lines, and they should use the new logger right away instead of `print`.

### Task 3.1: `logging` instead of `print` in the server

- **Finding (recommended):** the server uses `print`, so there are no levels and no
  timestamps, and every test run is full of "Client connected" lines.
- **Do:** create one module-level logger in `server.py` and configure it only in
  `if __name__ == "__main__"`, so libraries and tests stay quiet by default. Choose levels:
  `INFO` for connect/disconnect, `WARNING` for a failed handshake or a dropped bad client.
  Don't log passwords or whole requests, because `login`/`register` carry passwords.
  Use `logger.exception` only where you want the traceback.
- **Test:** `assertLogs` checks that a dropped bad client is logged at `WARNING`. The test
  output has no server lines.
- **Answer before coding:** Why configure logging only in the entry point and never in an
  imported module? Which requests must never be logged in full here, and why?
- **Commit:** `refactor: log server events with logging instead of print`
- **Read first:**
  - [Logging HOWTO](https://docs.python.org/3/howto/logging.html): the "when to use what" table
  - [TestCase.assertLogs](https://docs.python.org/3/library/unittest.html#unittest.TestCase.assertLogs)
  - [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html): what never to log

### Task 3.2: remove the overlapping `except` pair and the dead constant

- **Findings (recommended):** `except (ConnectionError, OSError)` appears in `server.py`
  and `client.py`. `ConnectionError` is a subclass of `OSError`, so listing both suggests
  a difference that doesn't exist. `BUFFER_SIZE` in `config.py` isn't used anywhere (and
  is still listed in `PLAN.md`'s structure tree).
- **Do:** keep the narrowest class that is still correct at each site (Task 1.1 may
  already have changed the server one). Delete `BUFFER_SIZE` and fix the `PLAN.md` tree.
- **Answer before coding:** When *is* it worth listing a subclass next to its parent in
  one `except`? (Hint: almost never; in separate clauses, order matters.)
- **Commit:** `refactor: drop redundant exception classes and an unused constant`
  (likely a trivial chunk with no journal entry; the skill decides)
- **Read first:** [Exception hierarchy](https://docs.python.org/3/library/exceptions.html#exception-hierarchy),
  [Yagni](https://martinfowler.com/bliki/Yagni.html): martinfowler.com

## Batch 4: protocol contract

Branch `fix/protocol-contract`.

### Task 4.1: end of stream isn't a valid `null` message

- **Finding (important):** `receive_message` (`protocol.py:21`) returns `None` at EOF, and
  `json.loads("null")` also returns `None`. A client that sends `null` is disconnected
  without a reply, while `[]` or `{}` get a proper error reply. The docstring promises
  "dict or None, raises JSONDecodeError", but the function returns any JSON value and can
  raise other errors.
- **Do:** make "connection closed" impossible to confuse with any decoded value. A
  dedicated exception and a unique sentinel object are both valid choices: pick one and
  say why in the journal. Decide which layer checks "the message is an object". Then add
  type hints to `protocol.py` and make the docstrings tell the truth.
- **Test:** `null` gets an error reply and the session goes on. EOF still ends the
  session. A unit test in `tests/test_protocol.py` covers each case.
- **Answer before coding:** When is a special return value safe, and when does it collide
  with a normal result? Should `protocol.py` know what a valid *request* is, or only what
  a valid *message* is?
- **Commit:** `fix: tell a closed connection apart from a null message`
- **Read first:**
  - [PEP 661: Sentinel Values](https://peps.python.org/pep-0661/) (now Final; see the `sentinel` entry in the docs)
  - [IOBase.readline](https://docs.python.org/3/library/io.html#io.IOBase.readline): what EOF looks like
  - [PEP 484: Type Hints](https://peps.python.org/pep-0484/)

### Task 4.2: decide what happens to a last frame without `\n`

- **Finding (recommended):** a complete JSON object without the final newline still runs
  when the client closes the connection. The reviewer did this with `stop`. The README
  says every message ends with `\n`.
- **Do:** choose between rejecting the frame as incomplete and documenting the tolerance,
  then make code, README "Protocol" and `PLAN.md` say the same thing. The NDJSON spec says
  each JSON text *ends with* a newline, so cite it in the decision.
- **Test:** the chosen behaviour, for example that a `stop` without `\n` followed by close
  does *not* stop the server, if you choose to reject it.
- **Commit:** `fix: reject an unterminated final frame` or
  `docs: document tolerance for an unterminated final frame`
- **Read first:** [NDJSON spec](https://github.com/ndjson/ndjson-spec),
  [Message framing](https://blog.stephencleary.com/2009/04/message-framing.html): Stephen Cleary,
  concept 002 in this repo

## Batch 5: resource and time limits

Branch `fix/server-limits`. Do this after batch 4, since both change `receive_message`.

### Task 5.1: maximum message size

- **Finding (important):** `readline()` has no limit, so a client that never sends `\n`
  can make the server use unbounded memory. Concept 002 already names this gap.
- **Do:** add `MAX_MESSAGE_SIZE` to `config.py`. Read at most one character past it so
  you can tell "line ended" apart from "line cut at the limit". On an over-long line,
  reply with an error and close the connection. The rest of that line is still in the
  stream, so it must never be parsed as the next message.
- **TLS note:** the limit counts characters in the text stream after TLS decryption, not
  bytes on the wire. State which unit the constant uses.
- **Test:** an over-long line gets an error and the connection closes. A message exactly
  at the limit works. A new client still gets an answer.
- **Answer before coding:** Why is it *wrong* to keep the session going after you cut a
  line short?
- **Commit:** `fix: limit the size of one message`
- **Read first:** [IOBase.readline](https://docs.python.org/3/library/io.html#io.IOBase.readline)
  (the `size` argument), [OWASP: Denial of Service](https://community.owasp.org/attacks/Denial_of_Service)

### Task 5.2: idle timeout for a session

- **Finding (important):** after the TLS handshake (`server.py:171`) the socket blocks
  with no timeout. With one client at a time, a client that logs in and then says nothing
  blocks everyone.
- **TLS note:** `TLS_HANDSHAKE_TIMEOUT` already covers silence *during* the handshake.
  This task covers silence *after* it.
- **Do:** add `CLIENT_IDLE_TIMEOUT` to `config.py`. When a read times out, close the
  connection. Don't keep reading: the docs warn that a `makefile()` stream may be in an
  inconsistent state after a timeout. Write down the known gap: an idle timeout doesn't
  stop a client that trickles in one byte at a time ("slowloris"), because only a total
  deadline per message or per session does. Decide whether to add one now or record it
  as a known gap.
- **Test:** a client that connects, logs in and sends nothing is dropped after the
  timeout (short timeout in the test), and the next client is served.
- **Commit:** `fix: drop clients that stay idle too long`
- **Read first:** [Notes on socket timeouts](https://docs.python.org/3/library/socket.html#notes-on-socket-timeouts),
  [socket.listen backlog](https://docs.python.org/3/library/socket.html#socket.socket.listen)

**Concept note candidate:** "One client at a time vs threads vs `selectors`: what does each
model cost?" Read [socketserver](https://docs.python.org/3/library/socketserver.html),
[selectors](https://docs.python.org/3/library/selectors.html) and
[Beej's guide, section 7](https://beej.us/guide/bgnet/html/split/slightly-advanced-techniques.html).
Changing the concurrency model is **not** in this plan. The review calls one client at a
time a conscious simplification, and limits are needed in every model. YAGNI.

## Batch 6: server lifecycle and clocks

Branch `fix/server-lifecycle`.

### Task 6.1: uptime from a monotonic clock

- **Finding (important):** `start_time = time.time()` (`server.py:48`). If the system
  clock goes backwards, uptime can go negative.
- **Do:** measure the duration with `time.monotonic()`. Keep the wall clock only for
  showing a start date, if you ever want one. `throttle.py` already takes an injectable
  clock, so follow that pattern to make the test deterministic.
- **Test:** with a fake clock, uptime equals the difference between the clock readings.
  No `sleep`.
- **Commit:** `fix: measure uptime with a monotonic clock`
- **Read first:** [time.monotonic](https://docs.python.org/3/library/time.html#time.monotonic),
  journal 005 (the same choice for the lockout)

### Task 6.2: an explicit way to close the server

- **Finding (recommended):** `__init__` binds the port, but the only way to close the
  socket is to run `serve_forever`. In `serve_forever`, `listen()` and `settimeout()` run
  before the `try`, so an error there leaves the socket open. The `__main__` block calls
  `server.sock.close()` by hand on two paths.
- **Do:** give `Server` a `close()` method, and maybe `__enter__`/`__exit__`, the same way
  `socketserver` has `server_close()`. Move all start-up work inside the guarded region,
  and use it in `__main__` and the tests.
- **Test:** after `close()` the port can be bound again. An exception during start-up
  doesn't leave the port taken.
- **Commit:** `refactor: give the server an explicit close and guard start-up`
- **Read first:** [socketserver: server_close](https://docs.python.org/3/library/socketserver.html)

### Task 6.3: no port hijacking on Windows

- **Finding (important, not verified by the reviewer):** on Windows, `SO_REUSEADDR` lets a
  second process bind a port that is already in use. Two servers can then run at once,
  and connections reach a random one of them.
- **Do:** first **reproduce it on your Windows machine**: start two servers on the same
  port and write down what happens. Then choose per platform. `SO_EXCLUSIVEADDRUSE` exists
  only on Windows (`hasattr(socket, "SO_EXCLUSIVEADDRUSE")`). On Linux and macOS,
  `SO_REUSEADDR` is still what you want for a quick restart after `TIME_WAIT`.
- **Test:** binding a second `Server` to the port of a running one raises `OSError`. That
  should hold on every OS once the fix is in.
- **Commit:** `fix: stop a second server binding the same port on Windows`
- **Read first:** [Microsoft: Using SO_REUSEADDR and SO_EXCLUSIVEADDRUSE](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse):
  read "Application Strategies"

**Concept note candidates:** "monotonic vs wall clock", "SO_REUSEADDR on Windows vs POSIX".

## Batch 7: client error handling

Branch `fix/client-errors`.

### Task 7.1: readable messages for every failure, no tracebacks

- **Finding (recommended):** only some failures are handled. The client shows a traceback
  instead of a message when:
  - the connection times out or the host can't be reached
  - the user presses Ctrl+C while waiting for a reply
  - the reply isn't a JSON object: an array or string gives `AttributeError` at
    `response.get`, and bad JSON or bad encoding raise their own errors
- **Do:** list every way the connection, the read and the decode can fail, and write the
  message the user should see for each one. Validate the reply before using it. The
  client trusts the server no more than the server trusts the client. Also tidy up the
  overlapping `except` pair if task 3.2 hasn't already.
- **Test:** create `tests/test_client.py`. Use `unittest.mock` to replace `input`, the
  socket and `receive_message`, so each failure is reproduced without a real server.
  Assert on the printed message.
- **Commit:** `fix: show clear client messages for network and reply errors`
- **Read first:** [unittest.mock](https://docs.python.org/3/library/unittest.mock.html):
  "where to patch"

### Task 7.2: don't wait for ever (server busy or silent)

- **Finding (recommended):** a second client never gets an answer while the server is busy
  with the first one.
- **TLS note:** with TLS, the client's `wrap_socket` handshake waits until the server calls
  `accept()`. So today a second client hangs *before* "Connected" is printed, with no
  message at all. A successful `connect()` only means the OS put you in the `listen()`
  backlog.
- **Do:** add timeouts for connect, handshake and each reply (constants in `config.py`).
  If the handshake times out, say the server may be busy with another client. If a reply
  times out, close the connection (same `makefile()` caveat as task 5.2).
- **Test:** a mocked socket that times out produces the busy message, and the client
  exits cleanly.
- **Commit:** `fix: time out and explain when the server does not answer`
- **Read first:** [socket.listen backlog](https://docs.python.org/3/library/socket.html#socket.socket.listen),
  [Notes on socket timeouts](https://docs.python.org/3/library/socket.html#notes-on-socket-timeouts)

## Batch 8: launcher cleanup and readiness

Branch `fix/launcher-cleanup`. `run.py` has no tests yet. Each task adds
`tests/test_run.py` cases using `unittest.mock` (patch `subprocess`, `sys.platform`,
`server_is_running`).

### Task 8.1: always clean up the server the launcher started

- **Finding (important):** if `main()` ends with an exception, most likely Ctrl+C during
  `wait_for_server`, the background server it started is left running without an owner.
  It keeps the port and keeps writing `server.log`. After a start-up timeout it gets
  `terminate()`, but nothing waits for it to exit.
- **Do:** wrap the background server's whole lifetime in `try/finally`, using `terminate`,
  then `wait` with a timeout, then `kill` as a last resort. The launcher owns only the
  process it started. Never touch a server that was already running on the port.
- **Test:** with `wait_for_server` patched to raise `KeyboardInterrupt`, the mocked
  process gets `terminate()` and `wait()`.
- **Commit:** `fix: always stop the background server the launcher started`
- **Read first:** [try/finally](https://docs.python.org/3/tutorial/errors.html#defining-clean-up-actions)

### Task 8.2: exit with the client's code

- **Finding (recommended):** `run.py` ignores the client's exit code, so it reports
  success even when the client failed.
- **Do:** pass on the client's `returncode`, or a launcher-specific non-zero code for
  launcher failures, and document the codes in the README.
- **Test:** a mocked `subprocess.run` returns 3 → `main()` exits with 3.
- **Commit:** `fix: exit with the client's exit code`
  (small, so it can be merged into 8.1 if the skill calls it trivial)
- **Read first:** [CompletedProcess.returncode](https://docs.python.org/3/library/subprocess.html#subprocess.CompletedProcess.returncode)

### Task 8.3: check it is *our* server, not just an open port

- **Findings (recommended):**
  - `server_is_running` only checks that *something* accepts TCP on the port. If another
    app has the port, the launcher prints "reusing it" and the client hangs.
  - The probe can't tell an idle server from a busy one.
  - Each probe shows up in the server log.
  - If a terminal window opened but the server inside it never started, the user gets an
    error after 5 s with no fallback.
- **TLS note:** today each probe is a plain-TCP connect, so the server logs
  "TLS handshake failed" up to 50 times while starting.
- **Do:** probe with a real protocol exchange under a short timeout: a TLS handshake with
  the pinned certificate, then `help`. Report three cases separately: "not ours", "busy"
  and "ready". For the window case, print what to check. **Don't** start a second server
  after the timeout, because the first one may just be slow (the reviewer's warning).
  Optional, only if it helps the tests: split `start_server_in_window` into one function
  per OS. The reviewer said this can wait.
- **Test:** a fake listener that accepts but speaks no TLS gives "not ours", and the
  launcher doesn't start a client against it.
- **Commit:** `fix: confirm the protocol before reusing a server on the port`
- **Read first:** [unittest.mock](https://docs.python.org/3/library/unittest.mock.html)

## Repo-specific skills (ideas)

The review found one *pattern* of mistakes, not just a list of bugs. These skills turn the
pattern into a checklist that Claude (and you) run while the code is written, instead of
in the next review. Each one lives in `.claude/skills/<name>/SKILL.md`. The `description`
is what triggers it, so it says *when* to use it, with the key case first.

**Design principles:**
- **Small and composable.** `learn-by-commit` stays the entry point and calls a checklist
  skill from its step 2 when the change touches the matching files. The skills don't
  repeat each other.
- **Built from this repo's real bugs.** Every checklist item points to the task above that
  taught it, so the skill is also a revision sheet.
- **Tested against history.** To check a new skill, run it against the pre-fix code
  (`git show 154c71b:server.py`). It should flag the bugs that batches 1–8 fixed. If it
  doesn't, the skill is too vague.
- **Built after the batch it encodes**, so it reflects what you learned rather than the
  plan's guesses. The `anthropic-skills:skill-creator` skill can help draft and test them.

| Skill | Trigger (`description` gist) | What it checks | Would have caught | Build after |
|-------|------------------------------|----------------|-------------------|-------------|
| `trust-boundary-check` | Use when code reads data from a socket, file, CLI args or env, in `server.py`, `protocol.py`, `client.py` | Traces bytes → text → parsed → validated, and lists the exceptions each step can raise. Requires a size limit, a time limit and a type check. Asks "what if the peer is not our client/server?" | 1.2, 4.1, 5.1, 5.2, 7.1, 8.3 | batch 5 |
| `error-handling-review` | Use when adding or changing `try`/`except`, or any network or I/O call | Is every network call covered, including inside `except`? Redundant parent/child classes? Does one session's error stay in its handler? Is the narrowest class caught? Is anything swallowed silently? | 1.1, 1.2, 3.2, 7.1 | batch 1 |
| `negative-tests` | Use when adding server or protocol behaviour, or fixing a bug | A table of hostile inputs: invalid UTF-8, huge int, deep nesting, `null`/array/number, over-long line, no `\n`, abrupt close/RST, silence. Every server test ends with "a new client still gets an answer". Optional seeded `random` fuzz loop (stdlib only) | 1.1, 1.2, 4.1, 4.2, 5.x | batch 2 |
| `resource-lifecycle` | Use when code opens a socket, file, thread or subprocess, or edits `run.py` or test setup | Who opens it, who closes it, what if start-up half-succeeds? `with` / `try-finally` / `addCleanup`; `terminate` → `wait` → `kill`; own only what you started | 2.1, 6.2, 8.1 | batch 8 |
| `logging-conventions` | Use when adding output to the server or launcher | Logger per module, configured only in `__main__`; level guide; never log passwords or raw `login`/`register` requests; quiet tests, `assertLogs` for important events | 3.1 | batch 3 |
| `cross-platform-check` | Use when touching socket options, signals, paths, file modes or `run.py` | Windows vs POSIX table: `SO_REUSEADDR`/`SO_EXCLUSIVEADDRUSE`, Ctrl+C in a blocking `accept()`, `CREATE_NEW_CONSOLE`, file modes vs ACLs, `python` vs `python3`. Asks for a manual Windows check where tests can't reach | 6.3, step 11 | batch 6 |
| `docs-drift-check` | Use before every commit that changes behaviour, commands, structure or protocol | Greps README, `PLAN.md`, docstrings, skills and concept notes for the names that changed; asks "which sentence is no longer true?" Could be a short section in `learn-by-commit` instead of its own skill | 4.1, 4.2, 9.1 | batch 9 |
